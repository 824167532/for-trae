## 本次修改的核心改动

### 🔧 改动1：发票检测 → 智能扫描整个月目录（含发票号识别）

**文件：** [file_service.py](file:///workspace/invoice_helper/services/file_service.py)

**原 `check_invoices_exist` 函数（需重写）：**
- 改为新函数 `detect_invoice_files(customer_path, settlement_month)`
- 扫描范围：`{根目录}/{客户路径}/{结算月份}/` 整个目录（含所有子目录递归）
- 识别规则（满足任一即判定为发票）：
  1. **扩展名匹配**：`.pdf` / `.ofd` / `.zip`
  2. **文件名含20位连续数字**（数电发票号格式为20位数字，如 `24117000000001234567`）
  3. **文件名含 "发票" / "invoice" 关键词**（作为辅助判断）
- 返回值：`{ "has_invoice": True/False, "files": ["file1.pdf", "file2.zip"], "file_count": 2 }`

**新增辅助函数 `_is_invoice_file(filename)`：**
```
输入: 文件名（不含路径）
输出: True/False

规则：
- 扩展名 ∈ {.pdf, .ofd, .zip} → 候选
- 同时满足：文件名中含有连续 20 位数字 或 包含"发票"/"invoice"关键词
- 不区分大小写
```

**注意：** `.xml` 从扩展名匹配中移除（因用户提到 zip 里面含 xml，不直接扫描 xml 文件）

### 🔧 改动2：「检查遗漏」→ 按"结算月份"扫描真实文件

**文件：** [todo_service.py](file:///workspace/invoice_helper/services/todo_service.py)

**重写 `get_missing_current_month`：**

**新逻辑：**
```
结算月份 = 系统当前月份（如 2026-06）

对"每个已登记的客户"做以下检查：
  扫描目录：{根目录}/{客户路径}/{结算月份}/
  → 用新的发票检测逻辑检查
  → 如果没找到发票 → 标记为"遗漏"

返回遗漏的客户列表
```

**关键变化对比：**

| | 旧逻辑 | 新逻辑 |
|-|--------|--------|
| 检查对象 | todos 表里有没有"待办记录" | 真实文件夹里有没有"发票文件" |
| 检查方式 | 查数据库 | 扫描文件系统 |
| 月份依据 | 待办记录里的 business_month | 系统当月（实际结算月份） |
| 判定遗漏 | 没创建待办=遗漏 | 没找到发票文件=遗漏 |

**为什么这样改？**
- 用户开票是按月结算的（比如 6 月就是 6 月的开票周期）
- 即使某客户的"业务归属月份"是 5 月，但用户在 6 月开了发票、放在 客户A/2026-06/ 目录下
- "检查遗漏"应该告诉您：**这个结算月份，哪些客户还没开过发票** — 而不是"哪些客户没登记待办"

**API 返回格式保持不变**（前端无需改）：
```json
[
  {"id": 3, "display_name": "客户C"},
  {"id": 5, "display_name": "客户E"}
]
```

### 🔧 改动3：「刷新状态」→ 同步升级为新的发票检测

**文件：** [todo_service.py](file:///workspace/invoice_helper/services/todo_service.py#L213-L252)

**`refresh_invoice_status` 函数适配：**
- 把 `file_service.check_invoices_exist()` 调用改为新的 `file_service.detect_invoice_files()`
- 关键点：**刷新状态仍按待办记录的 business_month 查找**（因为待办登记的是哪个月份，就去哪个月份文件夹找发票）
- 这样：创建了"客户A 2026-05"待办 → 刷新状态时去 客户A/2026-05/ 目录找发票
- 与"检查遗漏"的区别在于：检查遗漏是按当前结算月份检查所有客户是否有发票

**简单说：**
- 刷新状态 = "我已登记的待办 → 去对应月份文件夹看发票到了没"
- 检查遗漏 = "所有客户 → 这个月里谁的文件夹没发票"

## 风险说明

⚠️ **潜在风险：**
1. **文件名检测的准确率**：用户的发票文件名格式可能多样，20位数字检测是兜底但不保证100%。好处是同时有"发票/invoice"关键词作为双保险，且限定了 pdf/ofd/zip 三个扩展名，误判率极低。
2. **现有历史数据不受影响**：todos 表结构不变，不做数据迁移，仅改变"检测逻辑"。不会破坏已有数据。

✅ **向后兼容：**
- 数据库 schema 不变，不影响已有待办记录
- 前端 API 返回格式不变，不会破坏现有页面逻辑
- 仅是检测逻辑升级，已有功能全部保留
